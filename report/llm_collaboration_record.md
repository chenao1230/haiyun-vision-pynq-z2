# 大模型协作记录

本项目使用大模型辅助开展代码阅读、软硬件接口核查、算法调试、验证脚本编写与工程资料整理。协作过程中，团队负责提出应用需求、确定功能取舍、执行板卡操作和人工标注；模型负责将问题分解为可检查的技术环节，通过读取源码、运行工具及比较输出提出修改建议。方案是否采纳，以代码差异、测试日志、综合报告和实板结果为依据，模型生成的解释不单独作为功能正确或性能提升的证明。

## （1）协作方式与典型任务

项目采用“提出问题—检查证据—形成方案—独立验证—保留或否决”的工作流程。对于已经跑通的系统，先保留源码、参数和启动文件，再在独立副本中修改；对于算法比较，固定检测输入和人工标注，避免同时改变多个条件而无法解释结果。

典型协作工作按技术问题、实施方法和验证依据归纳于表4-2，具体纠错过程与方案取舍在后文展开。

**表4-2 典型技术问题与协作验证**

| 技术问题 | AI分析与实施 | 采纳依据与验证 |
| --- | --- | --- |
| 轨迹状态与显示框耦合，导致框位置滞后或尺寸收缩 | 沿检测、关联、绘制链路检查；利用detection_index关联当前检测框，保留卡尔曼状态用于后续匹配。 | 采纳状态与显示分离方案；分别评估内部框和显示框，不将绘制改善等同于检测精度提升。 |
| 遮挡与交会条件下的身份关联稳定性 | 冻结检测输入，独立编译跟踪器；按场景重置状态，逐帧核对ID、匹配索引及框坐标。 | 17组189帧重放与原输出一致；保留G111两次ID切换作为回归问题，未将主机验证等同于实板测试。 |
| 模型参数转换与HLS算子边界行为的可复现性 | 复核量化与BN融合；建立独立整数参考和输出哨兵检查，记录边界修复及同配置综合结果。 | 42个参数文件字节一致；修复后69,121个卷积输出及哨兵检查通过。共享出口未降低资源，未采纳其优化假设。 |

## （2）采纳的建议及其工程落实

跟踪框偏窄、位置滞后最初表现为界面问题，但其原因需要从检测、关联和绘制三个环节分别检查。协作中，模型提出：ByteTrack内部框用于运动预测与关联，显示框则可使用本帧匹配到的检测框。该方案通过detection_index建立轨迹与检测之间的对应关系，保持目标ID，同时减少内部滤波状态滞后对显示的影响。

项目采纳了这一分工，但没有将其解释为检测精度提高。若检测器本身漏检或只输出局部船体，替换绘制框并不能恢复完整目标。因此，后续评估分别统计内部框与显示框的结果，避免把显示改善误认为关联算法全面改善。

模型与硬件接口核查也采用了相同思路。针对SD浮点输入与以太网整数输入是否等价的问题，独立验证穷举了256种像素取值，并对3张实际图像进行预处理对照；针对参数导出，重新执行19个层的BN融合核验，导出的42个参数文件均与历史文件字节一致。团队采纳了“先验证格式与数值约定，再判断算法差异”的方法。由于这些检查没有发现转换错误，保留了原实现，没有为了形成修改记录而改动已经正确的代码。

## （3）自我纠错与验证过程

HLS复现提供了较为完整的纠错案例。初期数值测试通过后，协作流程继续增加输出缓冲区哨兵检查，发现单tile的3×3卷积虽然有效输出数值正确，却改写了有效区域之后的5408个元素。进一步检查循环控制发现，程序完成首个tile后仍无条件进入下一轮，退出判断发生过晚。

模型在独立副本中修正了循环边界，随后8项测试共69,121个有效输出逐位一致，输出哨兵检查也通过。这说明验证不能只比较“应当得到的结果”，还需要检查“不应发生的写入”。

该过程中也出现了模型新增测试代码自身的问题：局部变量名与原头文件宏定义冲突，导致编译失败。记录中保留了失败原因、修改方式和重跑结果，避免将测试工具错误误记为产品缺陷。

对于修复方案，模型还提出共享存储出口可能减少硬件重复逻辑的假设。但同配置HLS综合结果显示，共享出口版本并未比提前返回版本减少资源，LUT估算反而由103092增加至103141。因此，团队未采纳“该调整带来资源优化”的结论，只将其作为控制流程表达与边界修正进行记录。该案例属于独立算子实验，不能直接解释为现有船舶漏检或串ID问题已经得到修复。

## （4）未采纳或暂缓采纳的建议

团队对模型建议的筛选不仅考虑功能可行性，也考虑验证成本、板端开销和结论适用范围。主要取舍如表4-3所示。

**表4-3 模型建议的取舍与依据**

| 建议或初步判断 | 最终处理 | 判断依据 |
| --- | --- | --- |
| 通过局部复检改善重叠混框和漏检 | 未作为本次主线的必需步骤 | 额外推理增加计算开销，需要独立验证触发条件及收益；保留为扩展实验。 |
| 共享存储出口能够降低HLS资源占用 | 未采纳该性能结论 | 同条件综合数据未支持资源下降。 |
| 依据120 MHz综合约束描述发布系统运行频率 | 修正表述 | 发布FSBL初始化数组核查指向100 MHz配置；约束目标不能代替发布配置。 |
| 由相对深度直接得到船间距离或碰撞风险 | 未采纳直接报警方案 | 缺少可靠尺度、相机标定及现场距离真值，深度功能保留为估计扩展。 |
| 主机重放通过即可说明新版本实板通过 | 未采纳 | 主机执行、ARM构建、BOOT封装及实板运行属于不同验证阶段。 |

其中，时钟核查没有停留在工程目录名称或旧报告，而是进一步比较发布ELF中的PS初始化数组。15个初始化数组与对应源文件匹配，支持发布固件采用FCLK0为100 MHz的配置结论。

## （5）验证结果与团队经验

团队将这些经历整理为以下工程认识。

① 先明确比较条件，再讨论优化收益。输入尺寸、数据布局、量化尺度、检测阈值和运行时钟都可能改变结果，必须区分算法变化与测试条件变化。

② 把正确性分层验证。编译成功、数值一致、内存访问安全、时序通过和实板运行成功分别回答不同问题，不能相互替代。

③ 保留不支持预期的结果。某项修改没有减少资源，或某个场景仍有ID切换，也是确定方案边界的重要依据。

④ 把经验固化为开发流程和辅助工具。最新版Skill将输入接口、构建依赖、失败定位、修改记录和测试结果组织在同一目录中，并提供文件比较、数值对照及实现报告处理脚本，使后续成员能够按实际工程条件继续开发。

⑤ 人的核心作用在于确定目标与验收边界。模型可以扩大代码检查和方案探索的范围，团队仍需依据实际使用需求决定哪些功能进入主线、哪些保留为实验，以及哪些证据足以支持报告结论。
